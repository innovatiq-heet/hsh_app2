# Phonebook Favourites: Backend Handoff (`hsh_api`)

> **Date:** 2026-11-11 · **App side:** done in `hsh_app2` (branch `MVP-1.0.0`), already calling these endpoints. **Backend side:** to build, as described below.

## 1. What the feature is

In the admin **Student Phonebook**, a **Favourites** strip shows the students each admin or warden calls most. It fills itself: each call made from the phonebook is counted. A student who has been called **2 or more** times shows up there, with at most **10** students, most-called first.

The backend's job is to **store the call counts per logged-in user**, so the same favourites show on every phone that user logs in on.

The app is already built for these endpoints:

- Until they exist, every request gets a 404, and the app quietly falls back to counts kept on the phone.
- It keeps calls that failed to upload and sends them once the endpoints are live, so nothing is lost.
- **Don't change paths or field names without telling the app side.**

## 2. Rules

| Rule | Detail |
| :--- | :--- |
| **Auth** | Logged-in **admin** or **warden** only (same as the phonebook in the app). Any other role → `403`. Use the same auth middleware as the other admin routes. |
| **Per user** | All data belongs to `req.user.id`. One admin must never see another admin's favourites. |
| **Student key is opaque** | `student_key` is the phonebook's own id, e.g. `HSH-0768` (`HSH-` + bank code), or the student's name when the directory has no code. The phonebook comes from the external AVD VVN directory, so this is **not** `students.id`. Store it as a plain string. **Never** resolve it to a `students` row or use it for any action on a student. Bank codes collide with student ids; this once made a Screen Time lock hit the wrong student (see `hsh_app2/AGENTS.md` §4). Please add this rule to `hsh_api/AGENTS.md`. |
| **Retries are normal** | The app re-sends calls that failed to upload. Each call has a `client_call_id`. A repeated `(user, client_call_id)` must be **ignored, not counted, and not an error**. |
| **Response shape** | Same as the other routes: `{ "success": true, "data": … }` on success, and `{ "success": false, "message": "…" }` on error. |

## 3. Database

```sql
CREATE TABLE phonebook_call_logs (
  id               BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  user_id          INT UNSIGNED NOT NULL,          -- same type as users.id
  client_call_id   VARCHAR(64)  NOT NULL,          -- generated by the app; dedupes retries
  student_key      VARCHAR(100) NOT NULL,          -- e.g. "HSH-0768"; opaque, no FK
  student_name     VARCHAR(150) NULL,
  phone            VARCHAR(32)  NOT NULL,          -- as dialled, e.g. "+91 79849 07753"
  phone_normalized VARCHAR(32)  NOT NULL,          -- normalised by the app (10 digits)
  called_at        DATETIME     NOT NULL,          -- UTC
  created_at       DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uq_user_call (user_id, client_call_id),
  KEY idx_user_student (user_id, student_key),
  KEY idx_user_called (user_id, called_at)
);
```

Add it as a migration the usual way. A foreign key from `user_id` to `users.id` with `ON DELETE CASCADE` is fine. Don't add one on `student_key`.

## 4. Endpoints

Suggested location: a new module `src/modules/phonebook/` (`phonebook.routes.ts`, controller, service), mounted like the other modules.

### 4.1 `POST /phonebook/calls`: record calls

The app sends calls in batches: right after each call, plus any uploads that failed earlier.

**Request**
```json
{
  "calls": [
    {
      "client_call_id": "m3x9k2ab-ab12cd34",
      "student_key": "HSH-0768",
      "student_name": "Parth Patel",
      "phone": "+91 79849 07753",
      "phone_normalized": "7984907753",
      "called_at": "2026-11-11T09:30:00.000Z"
    }
  ]
}
```

**Validation** (anything invalid → `400` with a `message`):
- `calls` must be an array with 1–100 items.
- `client_call_id`: required, non-empty, at most 64 characters.
- `student_key`: required, non-empty, at most 100 characters.
- `student_name`: optional, at most 150 characters.
- `phone` and `phone_normalized`: required, non-empty, at most 32 characters.
- `called_at`: a required ISO date. If it's in the future, store the server's current time instead.

**Behaviour:** use `INSERT IGNORE` (or `ON DUPLICATE KEY UPDATE id = id`) inside one transaction.

**Response** `200`
```json
{ "success": true, "data": { "inserted": 1, "duplicates": 0 } }
```

### 4.2 `GET /phonebook/favourites`: the user's top students

**Query:** `limit` (default 10, max 50) and `min_calls` (default 2, min 1). The app sends `?limit=10&min_calls=2`.

**SQL** (two queries):
```sql
-- 1) top students
SELECT student_key,
       SUBSTRING_INDEX(GROUP_CONCAT(student_name ORDER BY called_at DESC SEPARATOR '\n'), '\n', 1) AS student_name,
       COUNT(*)       AS total_calls,
       MAX(called_at) AS last_called_at
FROM phonebook_call_logs
WHERE user_id = ?
GROUP BY student_key
HAVING total_calls >= ?
ORDER BY total_calls DESC, last_called_at DESC
LIMIT ?;

-- 2) per-number counts for those students
SELECT student_key,
       phone_normalized,
       SUBSTRING_INDEX(GROUP_CONCAT(phone ORDER BY called_at DESC SEPARATOR '\n'), '\n', 1) AS phone,
       COUNT(*) AS calls
FROM phonebook_call_logs
WHERE user_id = ? AND student_key IN (?)
GROUP BY student_key, phone_normalized
ORDER BY calls DESC;
```

**Response** `200`, in the order of query 1, with `last_called_at` as ISO UTC:
```json
{
  "success": true,
  "data": [
    {
      "student_key": "HSH-0768",
      "student_name": "Parth Patel",
      "total_calls": 7,
      "last_called_at": "2026-11-11T09:30:00.000Z",
      "numbers": [
        { "phone": "+91 79849 07753", "phone_normalized": "7984907753", "calls": 5 },
        { "phone": "98765 43210",     "phone_normalized": "9876543210", "calls": 2 }
      ]
    }
  ]
}
```
- `numbers` is sorted by `calls`, highest first. The app's quick-call button dials the first one.
- If there are no favourites, return `"data": []` with `200`, **not** a 404.

### 4.3 `DELETE /phonebook/favourites/:studentKey`: "Remove from Favourites"

- `:studentKey` arrives URL-encoded, e.g. `HSH-0768`, or `Parth%20Patel` for a name, so decode it.
- Run `DELETE FROM phonebook_call_logs WHERE user_id = ? AND student_key = ?`. This resets the count to zero. Calling the student again starts counting from scratch.
- **Response** `200 { "success": true, "data": { "deleted": 3 } }`. When nothing matched, either `200` with `deleted: 0` or `404` is fine; the app treats both as done.

## 5. Tests to add (`tests/e2e/phonebook-favourites.e2e.test.ts`)

1. POST a call, then GET with `min_calls=1`: the student appears with `total_calls: 1`.
2. POST the same `client_call_id` twice: it's counted once, and the second response reports `duplicates: 1`.
3. `min_calls` and `limit` are respected. The order is by `total_calls`, then the latest `last_called_at`.
4. `numbers` is grouped by `phone_normalized` and sorted by calls.
5. Admin A's calls never appear in admin B's GET.
6. DELETE removes only that user's calls for that student (another admin's are untouched), and GET no longer lists the student.
7. A student-role token gets `403` on all three routes. No token gets `401`.
8. Validation: an empty `calls` array, more than 100 items, or a missing `student_key` / `client_call_id` / `called_at` → `400`.
9. A `called_at` in the future is stored as roughly the current server time.

## 6. Optional
